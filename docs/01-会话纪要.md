## 第一部分：起点 —— 一篇 Nature 子刊论文

**论文**：*Learning vision-based agile flight via differentiable physics*
**出处**：Nature Machine Intelligence, Vol. 7, June 2025, pp. 954–966，DOI [10.1038/s42256-025-01048-0](https://doi.org/10.1038/s42256-025-01048-0)
**作者**：Yuang Zhang¹, Yu Hu¹, Yunlong Song², Danping Zou¹, Weiyao Lin¹（¹上海交通大学 ²苏黎世大学）

### 核心思想

用**可微物理仿真**把损失梯度直接反传穿过物理模型来训练端到端视觉飞行策略，而不是把动力学当黑箱（RL/模仿学习那样）。

四个关键设计：

1. **故意用极简质点模型**（只积分加速度/速度 + 一阶低通模拟飞控响应 + 二次空气阻力）。反常识但有效：换来更快的梯度计算和更平滑的优化地形。
2. **时间梯度衰减** `e^{−αΔt}`：抑制 BPTT 梯度爆炸，让监督信号只来自近未来。
3. **物理驱动损失** 4 项：速度跟踪（2 s 滑动平均 + Smooth L1）、避障（接近速度 × 截断二次 + softplus 势垒）、加速度/加加速度平滑。
4. **轻量网络**：深度图 max-pool 到 16×12 → 3 层卷积 → 192 维；姿态/目标速度投影后相加 → GRU（隐藏状态替代显式里程计）→ 输出推力加速度。

### 结果

- 森林峰值 **20 m/s**，零样本 sim-to-real
- 6 机无通信穿越窄门，涌现等待/跟随/让行等自组织行为
- 无里程计飞行（仅姿态 + 深度），速度预测误差 0.78 m/s
- 全部跑在 **21 美元单板机**上（4×A53 1.5 GHz + 1 GB RAM）
- 训练 1000 次迭代达 100% 成功率；达同奖励只需 PPO 的 10% 采样

**作者自己承认的局限**：视场角受限（偏航锁定目标方向）、急加减速时相机朝天/朝地、质点模型做不了特技机动、气阻需逐平台标定。

> 完整速读见 [04-论文速读-NMI敏捷飞行.md](04-论文速读-NMI敏捷飞行.md)

## 第三部分：12 个坑（现象 / 根因 / 解法）

### 坑 1：校园网 TLS 审计导致 git/curl 全部失败

- **现象**：`git clone` 报 `gnutls_handshake() failed`；curl 报证书错误；证书链里出现 `Scholar Verify`（校园网 SSL 中间人）。
- **根因**：校园网 SSL 审计代理，WSL 自带 CA 不认它的根证书。
- **解法**：从 Windows 证书库导出 `Scholar Root CA v1/v2`，装进 WSL 的 `/usr/local/share/ca-certificates/` + `update-ca-certificates`；临时可用 `git -c http.sslCAInfo=...`。
- **附**：大文件传输会被审计代理截断（`GnuTLS recv error -9`），需用 tarball + 断点续传替代 `git clone`。

### 坑 2：私有仓库 clone 卡在凭据提示

- **现象**：`git clone` 无输出、长时间挂起。
- **根因**：私有仓库且未提供凭据，git 在等用户名输入（无 TTY 时永久等待）。
- **解法**：用 `gh auth token` + `http.extraheader`；并设 `GIT_TERMINAL_PROMPT=0` 防止挂死。

### 坑 3：1.62 GB 仓库在 150 KB/s 网络下不可用

- **解法**：**blobless + 稀疏检出**，只取里程碑 A 需要的目录：
  ```bash
  git clone --filter=blob:none --no-checkout --depth 1 -b dev_wwa_air <repo>
  git sparse-checkout init --no-cone   # 只勾 src/sp_nav_bringup、sp_localization、sp_control、sp_robot_msg、sp_filght_sim、sp_communicator、bash
  git checkout -f dev_wwa_air
  ```
  1.62 GB → **181 MB**（跳过 VINS-Fusion 85 MB、ORB `Examples*` 约 600 MB 示例数据集）。
- **注意**：blobless 仓上跑 `git status` / 读文件会触发**懒加载网络请求**，可能卡死；`check_portable_paths.py` 这类遍历脚本要慎用。

### 坑 4（最关键的环境问题）：ros_gz 版本与 Gazebo 不匹配

- **现象**：桥接进程正常、话题能发现，但 **ROS 侧一条数据都收不到**，日志刷 `Unknown message type [8]/[9]`。
- **根因**：apt 的 `ros-humble-ros-gz-bridge 0.244.26` 依赖 **`libignition-transport11` / `libignition-msgs8`（Gazebo Fortress）**，而 PX4 v1.16 用 **Harmonic（gz-transport13 / gz-msgs10）**。两者能发现话题，但消息解不出来。
- **解法**：源码编译 **ros_gz 1.0.25**（Harmonic 线）到独立工作区，启动时先 source 它覆盖 apt 版本。配套做了 4 处本地适配：
  1. `gz_aliases/`：提供 `gz-transport` / `gz-msgs` 的 CMake 别名（系统只有带版本号的 `gz-transport13` / `gz-msgs10`）；
  2. 删掉 `marine_acoustic_msgs`（未安装的水下声学消息）相关 mappings/convert 源与头；
  3. `yaml-cpp::yaml-cpp` → `yaml-cpp`（系统 yaml-cpp 无命名空间目标）；
  4. `rclcpp::BestAvailableQoS()` → `rclcpp::QoS(KeepLast(10)).best_effort()`（Humble 无此 API）。

### 坑 5（最隐蔽）：ORB 同步队列造成 0.75 s 延迟 → 视觉位姿被全部丢弃

- **现象**：ORB 里程计正常 15 Hz、跟踪状态 OK，但 `/mavros/vision_pose/pose_cov` **一条都没有**；PX4 因此不解锁（`Arming denied: Resolve system health failures first`）。
- **根因**：`sp27_flight.launch.py` 里 `sync_queue_size: 30`，在 15 Hz 下等于缓存 **2 秒**画面，ORB 输出因此**固定落后仿真时钟 0.75 s**；而 `vio_bridge` 的陈旧阈值是 **0.3 s** → 每帧都被 `return std::nullopt` 静默丢弃（连警告都很少）。
- **解法**：`sync_queue_size` 30 → **3**。延迟 752 ms → **50 ms**，视觉位姿立刻恢复，解锁立刻成功。
- **诊断方法**（可复用）：写一个 rclpy 小程序订阅 `/orbslam3/raw_odom`，打印 `now - header.stamp`。

### 坑 6：仓库自身缺文件

- **现象**：ORB_SLAM3 的 CMake 报 `No SOURCES given to target: DBoW2 / g2o`。
- **根因**：CMakeLists 引用了、但仓库**从未提交**的文件：
  - `Thirdparty/DBoW2/DUtils/Timestamp.{h,cpp}`
  - `Thirdparty/g2o/g2o/stuff/timeutil.{h,cpp}`
- **解法**：从上游 `UZ-SLAMLab/ORB_SLAM3` 取同版本文件补齐。

### 坑 7：ORB 示例程序拖垮构建

- **根因**：46 个 `add_executable` 依赖 `Examples/`、`Examples_old/`（约 600 MB 数据集），稀疏检出没取。
- **解法**：在 `CMakeLists.txt` 的 `# Build examples` 处加 `option(SP27_ORB_BUILD_EXAMPLES ... OFF)` 开关（原文件备份 `.orig`）。里程碑 A 只需要 `libORB_SLAM3.so`。

### 坑 8：Pangolin 版本与布局

- **现象**：`orbslam3_ros` 的 CMake 硬编码找 `Pangolin/build/src` 下的 `libpangolin`。
- **根因**：Pangolin v0.8 改成 `components/` 布局，没有顶层 `include/`+`src/`。
- **解法**：用 **Pangolin v0.6**（经典布局）。且它未安装到系统时，`orbslam3_ros` 找不到头文件——用 `CPLUS_INCLUDE_PATH` 指向源码 `include/` **和** `build/src/include/`（`config.h` 是构建时生成的）。

### 坑 9：PX4 编译期需要联网拉 ExternalProject

- **现象**：`ninja` 阶段失败于 `PX4-OpticalFlow`、`Micro-CDR` 的 `git clone`（校园网不通）。
- **解法**（三处本地适配）：
  1. `boards/px4/sitl/default.px4board`：`CONFIG_MODULES_UXRCE_DDS_CLIENT=n`（我们用 MAVLink/MAVROS，不需要 uXRCE-DDS）；
  2. `src/modules/simulation/gz_plugins/CMakeLists.txt`：注释 `add_subdirectory(optical_flow)` 并从 `px4_gz_plugins` 依赖里移除（机体无光流传感器）；
  3. **新建 `Tools/simulation/gz/worlds/default.sdf`**：PX4 从 `worlds/*.sdf` 生成 `gz_<机型>_<世界>` 目标，缺 `default.sdf` 就没有 `gz_sp27_uav` 目标（launch 会报 `unknown target`）。

### 坑 10：GPS 子模块与 `GIT_SUBMODULES_ARE_EVIL`

- **现象**：`make px4_sitl` 内部 `git submodule update` 失败；且 ninja 报 `'devices/.git' missing`。
- **解法**：用 codeload **tarball** 解压到 `src/drivers/gps/devices`，放一个 `.git` 占位文件满足 ninja 依赖，并全程 `export GIT_SUBMODULES_ARE_EVIL=1`（**PX4 官方提供的开关**，跳过所有子模块检查）。

### 坑 11：MAVROS 启动即崩 —— 缺 GeographicLib geoid

- **现象**：`mavros_node` 启动后 `terminate called ... GeographicLib exception: File not readable /usr/share/GeographicLib/geoids/egm96-5.pgm`。
- **根因**：bootstrap 里装 geoid 的脚本失败（sourceforge 下载）。
- **解法**：手动下载 `egm96-5.tar.bz2`，解压到 `~/.local/share/GeographicLib/`，并 `export GEOGRAPHICLIB_DATA=$HOME/.local/share/GeographicLib` —— **免 sudo**。

### 坑 12：`rosidl_pycommon` 在 Humble apt 索引里不存在

- **现象**：`ros_gz_bridge` 构建时 `ModuleNotFoundError: No module named 'rosidl_pycommon'`。
- **根因**：Humble 的 apt 源里没有这个包（只有 iron/rolling 有）。
- **解法**：`apt-get download ros-iron-rosidl-pycommon`（**不需要 root**）→ `dpkg -x` 解包 → 把纯 Python 模块放进 `PYTHONPATH`。同时 `sp27_vio_compare.py` 也需要它。

## 第四部分：内存 —— 真正的系统级瓶颈

这是本项目**最折磨人**的部分，也是反复"卡死"的真凶。

### 现象

- DSH/浏览器/远程桌面随机卡死，报错 `0x800705AF`（系统资源不足）
- Gazebo 窗口全黑、`/clock` 不步进、ORB 变慢、视觉位姿消失

### 根因（实测数据）

**WSL 会把分配给它的内存配额全部吃满（page cache），剩下的才归 Windows。** 主机只有 15.7 GB：

| WSL 配额 | vmmemWSL 实测 | Windows 可用物理 | 结果 |
|---|---|---|---|
| 12 GB | — | **0.16 GB** | 必卡死 |
| 8 GB | 4.9 GB（仍上涨） | **0.89 GB** | 卡死 |
| 6 GB | 6.31 GB（吃满） | **0.44 GB** | 卡死 |
| 5 GB | 5.70 GB | 1.02 GB | **仿真 OOM**（WSL 可用仅 199 MiB，`/clock` 都起不来） |
| **6656 MB（最终）** | 5.70 GB | 0.94–1.4 GB | 可跑，但偏紧 |

Windows 侧的真实占用：**飞书 14 个进程 1.69 GB**、svchost 1.57 GB、DSH 1.47 GB、Edge 0.9 GB、NVIDIA 组件 0.85 GB、ToDesk/火绒/搜狗 0.55 GB —— Windows 自己要 8–9 GB。

### 最终配置（`.wslconfig`）

```ini
[wsl2]
networkingMode=mirrored
autoProxy=true
dnsTunneling=true
memory=6656MB      # 不能用小数（6.5GB 会被拒），单位写 MB
processors=24
swap=3GB

[experimental]
autoMemoryReclaim=dropcache   # 比 gradual 激进，主动把缓存还给 Windows
sparseVhd=true
```

### 有效缓解手段

1. **无 GUI 模式**（`HEADLESS=1`，PX4 自带开关）：WSL 从 3.5 GB 降到 **2.4 GB**，Windows 从 0.94 GB 回到 **2.37 GB**，三路数据仍满速 15 Hz。
2. **关闭飞书 + Edge**：腾出约 2.5 GB。
3. **关掉 WSL 里的 `unattended-upgrades`**（后台占 400 MB 且会突然抢 CPU）：
   ```bash
   sudo systemctl disable --now unattended-upgrades
   ```
4. **不要用远程桌面看仿真画面**：WSLg 窗口走 D3D12，在 RDP 会话里**必然黑屏**（窗口宿主进程是 `msrdc`，标题带 `[WARN:COPY MODE]`）。请在本机物理屏幕上看。

### 一个反直觉的教训

**工具调用超时会连坐杀掉仿真进程。** 我在一次检查里放了 70–90 秒的 `sleep`，DSH 侧超时中断命令时，`wsl.exe` 的进程树被一起清理，仿真停在半启动状态（服务器活着但只有 15 个话题、PX4 已退出、`/clock` 不步进、GUI 全黑）。**后来改用 `setsid nohup ... &` 完全脱离 + 短命令轮询**才稳住。

## 第五部分：接入官方 RMUC2027 场地后的新问题

### 资产安装

拿到了两个文件（负责人提供）：

| 文件 | 内容 |
|---|---|
| `meshes.zip`（23 MB） | 解压出 `meshes/model.dae`（**96 MB，130 个具名子网格**） |
| `RMUC2027_4.dae`（46.5 MB） | 另一个变体 |

严格校验：`model.dae` 的 130 个 geometry 名称 **完全覆盖** `model.sdf` 要求的 130 个 `<submesh>` 名（`ID3`/`ID6`/…）；`RMUC2027_4.dae` 则一个都对不上（是给别的模型用的）。

### 结果：能加载，但精度反而变差

| 指标 | 围栏世界（visual_feature_fence） | **真实场地（RMUC2027）** |
|---|---|---|
| 世界加载 | ✅ | ✅ 无报错 |
| 3D 位置误差 RMSE | **8.3 cm** | **44.8 cm** |
| 位置误差中位 | 6.1 cm | 32.5 cm |
| 姿态误差中位 | 0.55° | 3.29° |
| 真值高度 | 稳定 1.00 m | **一度 3.12 m**（94% 时间 >1.5 m） |

### 观测到的失败链条

1. 起飞正常（1.003 m）；
2. 进入内置航线后控制器反复报 `Turn paused: position error 0.20~0.27 m`（超过 `turn_position_limit_m: 0.25`）；
3. **PX4 主动退出 OFFBOARD**（`BUILTIN_ROUTE -> REMOTE: PX4 exited...`），模式变为 `STABILIZED`；
4. 位置估计**发散到 x=−154 m, y=126 m**（视觉/EKF 跑飞）；
5. 我们用 `mavros/set_mode AUTO.LAND` 强制降落，最终 z=0.024 m 落地。

### 尚未确定的根因（**待办**）

怀疑方向（按可能性排序）：

1. **ORB 在真实场地里丢跟踪 / 尺度漂移** —— 场地材质偏暗、纹理重复，特征质量可能不如专门设计的 feature fence；需查 `tracking.csv` 的 `tracking_state` 分布（2=OK 的占比）。
2. **场地自身几何干扰** —— 96 MB 网格的尺寸/位置可能让相机看到大量近距离结构，深度初始化异常。
3. **ORB 处理变慢导致延迟回升** —— 重场景下 `sync_queue_size=3` 仍可能跟不上（此前曾观测到延迟回涨到 0.944 s）。
4. **PX4 OFFBOARD 退出机制** —— 位置误差超限或 setpoint 流中断会触发 fail-safe，属正常保护，需先解决上游精度问题。

## 第七部分：换仿真器 / 脱离 WSL 的选型结论

### 核心判断

**换仿真器解决不了"依赖 WSL"的问题。** 真正绑定 Linux 的不是 Gazebo，而是 **PX4 SITL + MAVROS + ORB-SLAM3 + ROS 2** 这条验证栈。

| 组件 | Windows 原生 |
|---|---|
| PX4 SITL | ❌ 不发布 Windows 版（只有[未合并的 PR](https://github.com/PX4/PX4-Autopilot/pull/27297)） |
| MAVROS | ❌ 无 Windows 发行 |
| Gazebo (gz-sim) | ❌ 无 Windows 官方支持 |
| ORB-SLAM3 + Pangolin | ⚠️ 理论可编译，实际极痛 |

### 各方案评估

| 方案 | 解除 WSL | 本机硬件 | 迁移成本 | 验证语义 | 结论 |
|---|---|---|---|---|---|
| Isaac Sim / Lab | ❌（PX4 仍要 Linux） | ❌ 差 2 倍 | 极高 | 需重建 | 不可行 |
| Unreal + AirSim | ❌ | ⚠️ 勉强 | 高 | 需重建 | 不推荐（AirSim 已归档） |
| Unity / Godot | ❌ | ✅ | 极高 | 会变 | 不推荐 |
| **双系统 Ubuntu** | ✅ | ✅ | **低** | **完全保持** | **推荐** |
| 独立 Linux 机器 | ✅ | ✅ | 低 | 保持 | 有条件则最佳 |

### Isaac 旧版本也不行（用户提出过的思路）

- Isaac Sim 4.x/5.x 官方口径：**至少 32 GB 内存 + 16 GB 显存**；更早版本显存最低线一直是 8 GB、内存最低 16 GB。本机 15.7 GB / 8 GB **勉强够老版本最低线**。
- 但唯一成熟的 PX4+Isaac 方案 [Pegasus Simulator](https://github.com/pegasussimulator/PegasusSimulator) 官方声明：
  > "tested with Isaac Sim 5.1.0 on **Ubuntu 22.04LTS** … PX4-Autopilot **v1.14.3** … **This extension was not tested on Windows.**"
- 且 Pegasus 与 Isaac 版本强绑定（5.1.0↔5.1.0、4.5.1↔4.5.0、4.2.0↔4.2.0），并要求 **PX4 降级到 v1.14.3**（我们用 v1.16.2）。

**结论**：Isaac 可以用于"好看画面/合成感知数据"的独立课题，但**不能替代本项目的飞行闭环验证**；且它只是把内存压力从 WSL 搬到 Windows，总量不减反增。

## 第九部分：给后来人的经验清单

### 环境搭建顺序（照抄即可）

```
1. .wslconfig: memory=6656MB / processors=24 / swap=3GB / autoMemoryReclaim=dropcache
2. 校园网根证书 → WSL 信任库
3. bootstrap_root.sh（唯一一次 sudo）
4. 稀疏克隆仓库（181 MB）+ PX4 v1.16.2 + 关键子模块
5. patch_px4.sh（补丁 + 资源导出）
6. build.sh（Pangolin v0.6 → ORB_SLAM3 → colcon）
7. ros_gz 1.0.25 源码编译（独立工作区）
8. run_sim_headless.sh / run_sim.sh
9. verify_a.sh
```

### 最容易踩的三个点

1. **ros_gz 必须用 Harmonic 版**（apt 的是 Fortress，话题能发现但数据收不到）
2. **`sync_queue_size` 必须调小**（30 → 3），否则视觉位姿被静默丢弃、PX4 不解锁
3. **`GIT_SUBMODULES_ARE_EVIL=1` 与 `GEOGRAPHICLIB_DATA` 两个环境变量不能漏**

### 诊断方法论

- **分层隔离**：gz 单独 headless → +PX4 → +桥接 → +ORB，每层单独验证
- **量化延迟**：写 rclpy 探针打印 `now - header.stamp`，比看日志快得多
- **看进程数**而不是"是否启动"：`pgrep -fc "gz sim"` 应该是 2（服务器+GUI）或 1（headless）
- **分区要匹配**：`gz` CLI 必须先 `export GZ_PARTITION=<launch 日志里的随机分区>`，否则看不到任何话题
- **长时间操作必须脱管**：`setsid nohup ... &`，否则工具超时会连坐杀进程
